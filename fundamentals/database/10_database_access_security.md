# Database access roles and verified transport

Read [SQL foundations](01_databases_and_schemas.md) and the connection examples in [drivers](02_python_drivers.md) first. A bound parameter protects the SQL/data boundary. It does not decide which tables a connection may modify or whether the server at the other end is your intended database. This lesson develops those two boundaries.

## Separate the object owner from the running application

Alice's API needs to insert users and posts. A deployment also needs to add columns. If both use a table-owning account, an application bug or stolen credential can perform either action. PostgreSQL checks privileges using the connection's effective role; a table owner has powers that ordinary CRUD grants cannot subtract. Give the runtime role only the actions the application needs, and use a separate controlled migration identity that can become the owner.

| Identity | Owned state or authority | Intended use |
|---|---|---|
| `notes_owner` | Owns application schema and objects; cannot log in | Stable ownership across releases |
| `notes_migrator` | Can explicitly `SET ROLE notes_owner` | Reviewed deployment migrations |
| `notes_runtime` | Schema USAGE, selected table CRUD, sequence USAGE | API requests and ordinary jobs |
| Monitoring identity | Granted visibility needed for diagnostics | Observability tooling, separate from runtime |

Role membership is authority: anyone who can become the owner can change or drop its objects. Keep migration credentials out of the runtime service's environment. A NOLOGIN owner is useful because it separates object lifetime from a particular credential; it does not make its members harmless. The following lab uses `SET ROLE` through an administrator to demonstrate authorization. Real connections must authenticate separately through server/provider configuration.

### Build and exercise a disposable privilege boundary

Run this SQL in a fresh disposable PostgreSQL database with a lab administrator allowed to create roles. The names must be unused in that cluster because roles are cluster-wide. No passwords or authentication policy are embedded in the lesson. Provision real credentials through your secret manager/provider.

```sql
CREATE ROLE notes_owner NOLOGIN;
CREATE ROLE notes_migrator LOGIN NOINHERIT;
CREATE ROLE notes_runtime LOGIN;
GRANT notes_owner TO notes_migrator;
CREATE SCHEMA notes_app AUTHORIZATION notes_owner;

-- Default privileges belong to the role that will create future objects.
SET ROLE notes_owner;
ALTER DEFAULT PRIVILEGES IN SCHEMA notes_app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO notes_runtime;
ALTER DEFAULT PRIVILEGES IN SCHEMA notes_app
    GRANT USAGE ON SEQUENCES TO notes_runtime;
CREATE TABLE notes_app.users (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);
RESET ROLE;
GRANT USAGE ON SCHEMA notes_app TO notes_runtime;
-- For objects that existed before these defaults, explicit grants are required:
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA notes_app TO notes_runtime;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA notes_app TO notes_runtime;

SET ROLE notes_runtime;
INSERT INTO notes_app.users (email) VALUES ('alice@example.com') RETURNING id;
SELECT email FROM notes_app.users;
UPDATE notes_app.users SET email = 'alice+new@example.com' WHERE id = 1;
DELETE FROM notes_app.users WHERE id = 1;
RESET ROLE;
```

The INSERT returns 1 and SELECT returns Alice's email. Schema USAGE permits resolving the schema's objects; table INSERT permits adding a row. Sequence permissions matter for sequence-backed defaults such as SERIAL and explicit `nextval()` calls; identity-column generation has different privilege details, so test your actual mapping. The explicit sequence grant above also supports future SERIAL-backed mappings without granting ownership.

Now issue the intentional failure separately, outside an explicit transaction (psql's usual autocommit). With `ON_ERROR_STOP` enabled, run it as a separate invocation and expect a nonzero exit:

```sql
SET ROLE notes_runtime;
ALTER TABLE notes_app.users ADD COLUMN is_admin boolean;
-- ERROR: must be owner of table users
```

Reset the role before continuing in that same interactive connection. This failed statement proves the boundary; it does not prove the application cannot delete data, because DELETE was deliberately granted. Omit DELETE or grant fewer columns/tables if the actual application does not need them. Row-level security adds a separate tenant/row policy when required; schema/table privileges alone do not restrict Alice to Alice's row.

A migration connection should explicitly become `notes_owner` before creating objects. Creating a new table as `notes_migrator` without SET ROLE gives it a different owner and misses `notes_owner`'s future-object defaults. [PostgreSQL default privileges](https://www.postgresql.org/docs/15/sql-alterdefaultprivileges.html) apply to objects created later by the configured creator role, while [ordinary grants](https://www.postgresql.org/docs/15/ddl-priv.html) govern existing objects. On supported newer releases, role membership options differ; validate deployment SET ROLE behavior on the actual server.

For lab cleanup as the original administrator, after resetting any active role:

```sql
DROP SCHEMA notes_app CASCADE;
DROP OWNED BY notes_owner;
DROP OWNED BY notes_runtime;
REVOKE notes_owner FROM notes_migrator;
DROP ROLE notes_migrator;
DROP ROLE notes_runtime;
DROP ROLE notes_owner;
```

`DROP OWNED` removes remaining grants/default-privilege dependencies in this disposable database; never copy this cleanup into a shared production database. Other databases can still contain role dependencies if you reused these identities outside the lab.

## Make schema selection deliberate

Unqualified `SELECT * FROM users` resolves through `search_path`. If someone can create objects in a searched schema, they may influence which object or function the application resolves. PostgreSQL 15 changed fresh-database defaults for the public schema, but upgraded databases and customized grants can retain older permissions. Inspect actual grants rather than assuming the version alone secures the schema.

Use explicit application schemas in mappings/migrations or configure a controlled search path, with no schemas writable by untrusted roles. Runtime schema USAGE is different from CREATE: the lab grants USAGE and keeps CREATE with the owner. SECURITY DEFINER functions need a controlled search path and carefully restricted EXECUTE grants; they are a privileged interface, not a shortcut around this model. See [schema security](https://www.postgresql.org/docs/15/ddl-schemas.html).

## Encryption and verified server identity answer different questions

A server certificate chains to a trusted CA and identifies an expected hostname. Verification has two parts: trusting that chain and matching the requested endpoint to the certificate. Encryption alone can still connect to an impostor. In libpq, `sslmode=verify-full` requests both checks; `require` is not the same policy. Use the database's actual DNS endpoint and CA bundle from its operator/provider. An IP address requires a certificate matching that IP. Unix-domain connections have a different local trust boundary and do not exercise TLS.

These are deployment configuration excerpts. They need a reachable TLS-enabled database, an operator-provided CA file and credentials, and must be tested against that environment.

### Psycopg 3 and the SQLAlchemy psycopg dialect

```python
import os
import psycopg

with psycopg.connect(
    host=os.environ['DB_HOST'],
    dbname=os.environ['DB_NAME'],
    user=os.environ['DB_USER'],
    password=os.environ['DB_PASSWORD'],
    sslmode='verify-full',
    sslrootcert=os.environ['DB_CA_FILE'],
    connect_timeout=5,
) as conn:
    print(conn.execute('SELECT current_user').fetchone())
```

For SQLAlchemy use `postgresql+psycopg` and pass the same libpq settings through `connect_args` or appropriate URL parameters. Construct URLs with `URL.create()` when credentials contain URL-special characters. Avoid printing connection arguments or unredacted URLs. [Libpq SSL modes](https://www.postgresql.org/docs/15/libpq-ssl.html) and [Psycopg connections](https://www.psycopg.org/psycopg3/docs/api/connections.html) define this interface.

### asyncpg and the SQLAlchemy asyncpg dialect

asyncpg uses a Python SSL context rather than libpq's connection keyword set in this explicit configuration:

```python
import os
import ssl
import asyncpg

async def connect_verified():
    tls = ssl.create_default_context(cafile=os.environ['DB_CA_FILE'])
    # The default context requires a trusted chain and hostname verification.
    return await asyncpg.connect(
        host=os.environ['DB_HOST'],
        database=os.environ['DB_NAME'],
        user=os.environ['DB_USER'],
        password=os.environ['DB_PASSWORD'],
        ssl=tls,
        timeout=5,
    )
```

The caller owns the returned connection and must close it in `finally`. For `create_async_engine()` with `postgresql+asyncpg`, pass `connect_args={'ssl': tls}`. Do not send libpq-only `sslrootcert` or `options` kwargs directly to asyncpg. Keep the CA trust policy explicit rather than disabling hostname verification to make a mismatched endpoint work. See [asyncpg connect](https://magicstack.github.io/asyncpg/current/api/index.html#asyncpg.connection.connect) and [Python's default SSL context](https://docs.python.org/3/library/ssl.html#ssl.create_default_context).

With a pool/proxy, identify every transport leg: application→proxy and proxy→PostgreSQL. A verified first leg does not establish how the second is protected. Validate the proxy/server TLS configuration with the operators; [pooling](05_connection_pooling.md) owns proxy state and capacity behavior.

## Verify the boundary and diagnose the failing layer

In a staging environment, test a valid connection and one using an unrelated CA file; the latter must fail before SQL executes. Test a hostname that resolves to the server but is absent from its certificate; it must also fail. Keep password, CA and hostname variables separate so the cause is observable. Confirm a certificate rotation using overlapping trusted roots during the operator's rotation window, then remove the retired trust root according to policy.

A DNS/TCP timeout, certificate failure, authentication rejection, schema-USAGE rejection and table-privilege rejection occur at different layers. Report the layer and sanitized exception class/SQLSTATE rather than logging a full DSN. A `permission denied for sequence` on a SERIAL-backed INSERT points to a sequence grant; a missing schema privilege is not repaired by granting table SELECT. Recreate/test fresh tables after migrations to prove future defaults as well as existing grants.

The excerpts were exercised with Psycopg 3.3.6 and asyncpg 0.31.0 against a disposable PostgreSQL 15.17 server with a localhost certificate: valid CA/hostname succeeded, unrelated CA and mismatched hostname failed for both drivers. Deployment negative tests still require the actual certificate-bearing endpoint. A successful Unix-socket lab validates role behavior only; it cannot prove TLS verification. [Recovery](08_backup_and_recovery.md) also needs access to backups and keys under a separate operational identity.

## Transfer: a newly deployed table rejects writes

Yesterday runtime INSERT worked. Today's migration created `notes_app.posts`; runtime SELECT now reports permission denied. The migration used `notes_migrator` directly, while default privileges were set for `notes_owner`. Should you give runtime membership in the owner role?

No. The creator role determines the applicable default privileges. Inspect the new object's owner, apply the intended grants, and fix migrations to SET ROLE before object creation. Owner membership would let the runtime alter/drop objects and erase the boundary demonstrated above. Retest with another disposable future object so the next deployment is covered. If the failure instead occurs during the TLS handshake, changing table grants cannot affect it; investigate endpoint identity and CA trust first.
